## Assets
- **Daemon auth token** (`daemon-token.tmp`): 256-bit random hex string, mode 0o600, generated on daemon startup.
- **sessionStorage token**: Client-side copy of the auth token, stored in browser sessionStorage (not persistent across sessions).
- **WebSocket connection**: Real-time bidirectional channel between dashboard and daemon.

## Threat Landscape

### 1. Token Disclosure via URL (RESOLVED)
**Threat:** Token appears in browser history, Referer headers, proxy logs, and server access logs when sent as URL query param `?token=`.
**Impact:** Attacker with access to logs/browser history can replay the token.
**Mitigation (AUTH-01/02):** Token now sent via `Authorization: Bearer` HTTP header on WebSocket upgrade — header is not logged by proxies, not stored in browser history, not sent in Referer.
**Residual risk:** Proxy operators could configure header logging — mitigated by using loopback bind (127.0.0.1) by default.

### 2. XSS Token Theft
**Threat:** Malicious script injected into dashboard page reads token from sessionStorage and exfiltrates.
**Impact:** Attacker can authenticate as the user to the daemon WebSocket endpoint.
**Attack vector:** Dashboard serves user-controlled content (project files rendered in UI). The `location.host` origin check on WebSocket prevents cross-origin upgrade requests.
**Mitigation:** Token is in sessionStorage (not a cookie with automatic transmission). An XSS payload must explicitly call `sessionStorage.getItem("token")` and send it out. No HttpOnly/secure cookie flags because this is a JS-accessible secret.
**Scope:** The XSS attacker has the same session privileges as the user — this is inherent to any XSS. The auth token being JS-readable is a known trade-off for this architecture.
**Hardening:** Consider Content-Security-Policy restricting inline scripts.

### 3. Logout / Token Invalidation
**Threat:** User wants to invalidate their token (e.g., leaving a shared workstation).
**Current behavior:** Token is in sessionStorage — clearing sessionStorage immediately invalidates (token no longer sent on WebSocket reconnect). Daemon has no active session invalidation list — but daemon-token.tmp is regenerated on daemon restart, and the current token remains valid until daemon restarts.
**Mitigation:** The user or a session owner can:
  1. Clear sessionStorage in browser DevTools (immediate effect for reconnects).
  2. Restart the daemon — daemon-token.tmp is deleted on graceful shutdown (SIGTERM/SIGINT), forcing new token generation on next start.
**No active revocation list exists** — this is acceptable for single-user local SPA where token lifetime is bounded by daemon uptime.

### 4. Token Rotation
**Threat:** Token is compromised and needs to be rotated.
**Mechanism:** Token is regenerated on every daemon restart (wolf-daemon.ts lines 22-35). The file `daemon-token.tmp` is deleted on graceful shutdown.
**Trigger:** User runs `openwolf daemon restart` (or equivalent SIGTERM to the daemon process). Next start generates a new 256-bit token.
**Limitation:** Active WebSocket connections are not immediately invalidated — they will reconnect with the new token or fail auth naturally.
**No scheduled rotation** is implemented. Rotation is on-demand only.

### 5. Browser History / Cache
**Threat:** Token URL param persisted in browser back-forward cache.
**Mitigation (AUTH-01):** Token is no longer in URL. Browser history does not contain the token.

### 6. Proxy/Server Access Logs
**Threat:** Standard HTTP access logs capture request URLs including query strings.
**Mitigation (AUTH-02):** Token is in Authorization header — standard proxy access logs capture only the path (`/ws`), not headers. Token does not appear in access logs.

## Security Properties
- **Authentication:** Token validated via constant-time comparison (crypto.timingSafeEqual) in daemon verifyClient.
- **Authorization:** Token grants access to daemon WebSocket endpoint serving .wolf/ state.
- **Transport security:** By default, daemon binds to 127.0.0.1 — not exposed to LAN. Set bind to "0.0.0.0" only for multi-machine setups (with associated risk).
- **No session list:** Daemon does not track issued tokens — stateless validation against the secret file.

## Out of Scope
- Authentication model rewrite (SSO, OAuth): transport only, not auth identity
- Multi-user auth: single-user local daemon design
- HTTPS/TLS: SPA connects over ws:// (loopback) — upgrade to wss:// for network exposure
- Content injection in dashboard: XSS in user project files is a known trade-off of the feature set
