    **OVERWRITE** src/hooks/shared.ts (which is currently 753 lines) with a thin
    barrel of approximately 25-30 lines. The new file is a facade only — it
    imports nothing of its own; it re-exports from the six wolf-* modules.

    The new file MUST contain exactly these 7 statements (plus a file header
    comment) in this order:

    1. File header comment block (5-8 lines) explaining:
       - shared.ts is the public API of the hook subsystem (D-03)
       - It re-exports from internal wolf-* modules (D-03)
       - Consumer imports from `./shared.js` continue to work (HOOK-02)
       - The wolf-* modules are INTERNAL and not part of the public API

    2. `export { getWolfDir, getSessionDir, getWorktreeContext, normalizePath } from "./wolf-paths.js";`
       — Note: the source `getWorktreeContext` function in wolf-paths.ts uses
       the `WorktreeContext` return type. The type itself is re-exported as a
       TYPE (not a value) on its own line below.

    3. `export { ensureSessionDir, ensureWolfDir, isWolfFile, readMarkdown, appendMarkdown } from "./wolf-files.js";`
       — Per D-09, `ensureSessionDir` lives in wolf-files.ts (not wolf-paths.ts)
       and `normalizePath` is NOT in this list (it lives in wolf-paths.ts).

    4. `export { readJSON, writeJSON } from "./wolf-json.js";`
       — Per D-05, `isPlainObject` and `deepMergeDefaults` are NOT re-exported
       (they are internal to wolf-json.ts and not part of the original
       shared.ts public surface).

    5. `export { AnatomyEntry, parseAnatomy, serializeAnatomy } from "./wolf-anatomy.js";`
       — `AnatomyEntry` is an interface (type). TypeScript re-exports it
       transparently via the value-position export; no `export type` needed
       here (D-02 example code uses this form).

    6. `export { extractDescription } from "./wolf-describe.js";`

    7. `export { estimateTokens, timestamp, timeShort, readStdin } from "./wolf-misc.js";`

    8. `export type { WorktreeContext } from "./wolf-paths.js";`
       — This MUST be its own line. The `WorktreeContext` type is used by
       `getWorktreeContext`'s return signature; consumers may want to import
       the type. Per RESEARCH.md Pitfall 6, a separate `export type` line
       avoids the isolatedModules gotcha and ensures the type re-export
       works under `module: Node16`.

    **Critical rules:**
    - Use `.js` extensions in the `from "./X.js"` paths (required by
      tsconfig.hooks.json's `module: Node16` / `moduleResolution: Node16`).
    - DO NOT add any local `import` statements — the barrel does not
      consume anything directly.
    - DO NOT add a `default` export — every existing consumer uses named
      imports, and adding a default would create a new (unwanted) public
      surface entry (D-03).
    - DO NOT remove the existing file by deletion-then-creation. The
      executor should use the Write tool to replace the file contents.
      Do not use Edit on a 753-line file — Write is the correct tool here.
    - Preserve the .js extensions in re-export paths even though the
      TypeScript convention is to import from `./wolf-paths` (no extension)
      in many configs. The project's tsconfig.hooks.json uses Node16
      module resolution, which REQUIRES the .js extension on relative
      imports. The D-02 example in CONTEXT.md shows the .js extension.
    - File ends with a single trailing newline (POSIX convention; matches
      the other wolf-* files created in 02-01).
    - Total line count target: 25-30 lines (header comment + 7 export
      statements + a blank line between groups for readability).
