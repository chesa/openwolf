<objective>
Implement advisory per-file locking for concurrent `.wolf/` write safety. Hook processes (session-start, pre-read, post-read, pre-write, post-write, stop) run as separate Node.js processes that can race writing to the same files (`_session.json`, `token-ledger.json`, `buglog.json`). A new `withFileLock` utility, created in a dedicated `wolf-lock.ts` module, wraps every `writeJSON` call with O_EXCL-based file locking.

Purpose: Prevent data corruption when concurrent hook processes write to the same `.wolf/` JSON file. The lock is per-file, advisory, cross-process, and uses zero external dependencies.
Output: `wolf-lock.ts` module, wrapped `writeJSON` in `wolf-json.ts`, re-export in `shared.ts`.
</objective>

  <action>
  Create `src/hooks/wolf-lock.ts` — a self-contained module providing advisory per-file locking using Node.js built-in `fs.openSync` with `O_CREAT | O_EXCL`.

  Import conventions: `import * as fs from "node:fs"`, `import * as path from "node:path"`. No relative imports (this module is standalone). Named exports only.

  ### Constants
  ```typescript
  const LOCK_TTL_MS = parseInt(process.env.WITH_FILE_LOCK_TTL_MS || "30000", 10);
  const MAX_RETRIES = 10;
  const RETRY_DELAY_MS = 50;
  ```

  ### `acquireLock(lockPath: string): number | null`
  - Loop up to `MAX_RETRIES` times:
    1. Try `fs.openSync(lockPath, fs.constants.O_CREAT | fs.constants.O_EXCL)` — returns fd on success
    2. On `EEXIST`: check staleness via `fs.statSync(lockPath).mtimeMs`. If `Date.now() - mtimeMs > LOCK_TTL_MS`, unlink the stale lock and retry (continue loop). Do NOT attempt to acquire in the same iteration — let the loop restart `openSync`.
    3. On staleness check failure (race with another process deleting the lock): catch the error silently, continue loop
    4. Between retries: use `Atomics.wait(new Int32Array(new SharedArrayBuffer(4)), 0, 0, RETRY_DELAY_MS)` for non-blocking sleep
  - Return `null` if all retries exhausted

  ### `releaseLock(fd: number, lockPath: string): void`
  - `try { fs.closeSync(fd); } catch { /* ignore */ }`
  - `try { fs.unlinkSync(lockPath); } catch { /* ignore */ }`
  - Never throws — cleanup is best-effort

  ### `withFileLock<T>(filePath: string, fn: () => T): T`
  - Compute `lockPath = filePath + ".lock"`
  - Call `acquireLock(lockPath)` — if null, throw `Error("Could not acquire lock for ${filePath} after ${MAX_RETRIES} retries")`
  - `try { return fn(); } finally { releaseLock(fd, lockPath); }`
  - The `finally` block ensures lock release even if `fn()` throws

  Notes:
  - Use `Atomics.wait` NOT `setTimeout` — Atomics is synchronous and doesn't require async. `Atomics.wait` with a zero-value buffer and a timeout is a well-known pattern for synchronous sleep in Node.js.
  - Do not use `import * as crypto` — not needed for locking (only for writeJSON temp files).
  - The lock file is a zero-length sentinel file. Its purpose is existence + mtime, not content.
  - Per D-01: no external npm packages. All Node.js built-ins.

  ### Error handling edge cases:
  - If `unlinkSync` on a stale lock fails (e.g., permissions), continue the retry loop — `openSync` will fail again with `EEXIST`. Eventually retries exhaust and the error surfaces to the caller.
  - If the lock file is deleted between the stat check and the `unlinkSync` call (race), catch `ENOENT` silently and continue the retry loop.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02-01 | Denial of Service | Lock file orphaned after crash | mitigate | Staleness TTL (30s default, configurable via `WITH_FILE_LOCK_TTL_MS`) breaks orphaned locks |
| T-03-02-02 | Tampering | Symlink attack on `.lock` file | mitigate | `O_CREAT | O_EXCL` refuses to follow symlinks — `openSync` fails with `EEXIST` if the symlink target exists, preventing TOCTOU |
| T-03-02-03 | Information Disclosure | Lock file reveals file paths | accept | Lock filename is `{targetPath}.lock` — the target path is already visible in `.wolf/` listing |
| T-03-02-04 | Tampering | Race: stale lock detected, deleted, but another process creates new lock before we retry | accept | Valid retry-loop behavior — the loser retries on next iteration; at most one process holds the lock at any time |
