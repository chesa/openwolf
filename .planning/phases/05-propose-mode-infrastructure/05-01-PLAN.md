<objective>
Create the propose-mode infrastructure: an `appendProposal()` helper that stages learnings to per-session files instead of directly editing shared markdown, and update the OPENWOLF.md protocol to redirect Claude's learning writes to the staging path.

**Purpose:** Eliminate the race condition where concurrent Claude Code sessions (from git worktrees) silently overwrite each other's entries in `cerebrum.md` and `anatomy.md`. Proposals accumulate in session-scoped staging files; a separate merge phase (Phase 6) consolidates them into shared markdown under lock.

**Output:**
- `appendProposal(target, content)` function in `src/hooks/wolf-files.ts`
- `appendProposal` re-exported from `src/hooks/shared.ts`
- Updated `src/templates/OPENWOLF.md` directing Claude to the staging path
</objective>

    **In `src/hooks/wolf-files.ts`:** Add an `appendProposal` function below the existing `appendMarkdown` (line 87). The function must:

    1. Accept two parameters: `target: 'cerebrum' | 'anatomy'` and `content: string`.
    2. Resolve the session directory via `getSessionDir()` (imported from `./wolf-paths.js` — already imported at line 3).
    3. Build the proposal file path as `path.join(getSessionDir(), "proposed-learnings.md")`.
       - `getSessionDir()` already returns `.wolf/sessions/<worktreeId>/` in worktree mode and `.wolf/` in single-repo mode — no new path logic needed.
    4. Ensure the parent directory exists with `fs.mkdirSync(dir, { recursive: true })` (same pattern as `appendMarkdown` at line 85).
    5. Append a timestamped, target-tagged entry to the file using `fs.appendFileSync`. Entry format:

       ```
       
       ## TIMESTAMP → TARGET
       
       CONTENT
       ```

       Where:
       - `TIMESTAMP` = `new Date().toISOString()` (use the `timestamp()` export from `wolf-misc.ts`, already available — or inline `new Date().toISOString()`).
       - `TARGET` = the `target` parameter value.
       - `CONTENT` = `content.trim()`.
       - The leading newline ensures clean separation between entries (even if the file is initially empty — the blank entry before the first section heading is harmless markdown).
    6. **Do NOT** add error handling beyond what `appendMarkdown` already does — let any `fs` errors propagate. The calling hook's top-level catch will log and exit 0.
    7. **Do NOT** call `ensureSessionDir()` — `getSessionDir()` works without it (returns `getWolfDir()` fallback when worktree context is absent). The `ensureSessionDir()` call belongs in the hook that calls `appendProposal`, not in the helper itself.

    The function body should be ~10 compact lines. Reuse the `appendMarkdown` pattern for mkdir + appendFileSync.

    ```
    ## Cerebrum Learning (MANDATORY — every session)
    
    OpenWolf's value comes from learning across sessions. You MUST append learnings to the per-session staging file whenever you learn something useful. This is not optional.
    
    **Append to `.wolf/sessions/<worktreeId>/proposed-learnings.md`** (or `.wolf/proposed-learnings.md` in single-repo mode) — NOT directly to `cerebrum.md` or `anatomy.md`. Staging entries are reviewed and merged later. This ensures concurrent sessions cannot overwrite each other's learnings.
    
    **Entry format:**
    
    ```
    
    ## TIMESTAMP → TARGET
    
    CONTENT
    ```
    
    Where `TARGET` is `cerebrum`, `anatomy`, or a subsection name. Each entry is a separate section so they can be parsed and merged independently.
    
    **When to learn (same criteria, new destination):**
    
    **Update `## User Preferences` when the user:**
    - Corrects your approach ("no, do it this way instead")
    - Expresses a style preference (naming, structure, formatting)
    - Shows a preferred workflow or tool choice
    - Rejects a suggestion — record what they preferred instead
    - Asks for more/less detail, verbosity, explanation
    
    **Update `## Key Learnings` when you discover:**
    - A project convention not obvious from the code (e.g., "tests go in __tests__/ not test/")
    - A framework-specific pattern this project uses
    - An API behavior that surprised you
    - A dependency quirk or version constraint
    - How modules connect or data flows through the system
    
    **Update `## Do-Not-Repeat` (with date) when:**
    - The user corrects a mistake you made
    - You try something that fails and find the right approach
    - You discover a gotcha that would trip up a fresh session
    
    **Update `## Decision Log` when:**
    - A significant architectural or technical choice is made
    - The user explains why they chose approach A over B
    - A trade-off is explicitly discussed
    
    **The bar is LOW.** If in doubt, add it. A staging entry that's slightly redundant costs nothing. A missing entry means the next session repeats the same discovery process.
    ```
